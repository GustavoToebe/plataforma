# plataforma

Parent Maven e código que os backends da plataforma (Central, Servirea, consultoria-app e os próximos) precisam fazer **igual**. Fica fora dos sistemas para ser corrigido em um lugar só.

## O que entra aqui

Só infraestrutura que é igual nos sistemas e não depende do domínio: assinatura da integração, TOTP, limites de login e, aos poucos, erros e filtros web, monitoramento, base de testes, login e o lado do app do contrato com a Central. Regra de negócio de um sistema (financeiro, escalas, cobranças, treinos) **fica no sistema**.

## Estrutura

| Pasta | O que é | Artefato |
|---|---|---|
| `plataforma-parent/` | POM pai dos backends: Java 25, Spring Boot 4.1.x, Error Prone, JaCoCo, Surefire/Failsafe, imagem do Postgres dos testes | `br.com.plataforma:plataforma-parent` |
| `plataforma-comum/plataforma-comum-seguranca/` | HMAC da integração, TOTP e núcleo do limite de login; sem Spring e sem banco | `br.com.plataforma:plataforma-comum-seguranca` |
| `plataforma-comum/plataforma-comum-web/` | `ApiError` e `ApiException` (e as exceções 400/401/403/404/409/429), handler global de erros, `RequestIdFilter`, `LimiteCorpoFilter`; autoconfigurado (`PlataformaWebAutoConfiguration`) | `br.com.plataforma:plataforma-comum-web` |
| `plataforma-comum/plataforma-comum-monitoramento/` | `GET /monitoramento/metrics` em texto Prometheus (requisições, JVM, pool de conexões) com credencial exclusiva (`MonitoramentoFilter`); métricas do domínio entram por `MetricasDeDominio`; autoconfigurado | `br.com.plataforma:plataforma-comum-monitoramento` |
| `plataforma-comum/plataforma-comum-auth/` | Login, JWT com versão de credenciais, refresh opaco com rotação e reuso, cookie/CSRF por app, MFA (TOTP) e limite de login, no schema `plataforma` com Flyway próprio; ligado por `plataforma.auth.habilitado` | `br.com.plataforma:plataforma-comum-auth` |
| `plataforma-comum/plataforma-comum-central/` | Lado do app do contrato de integração v1 com a Central: filtro HMAC de entrada com nonce, cliente assinado de saída, idempotência do provisionamento e direitos locais, no schema `plataforma_integracao` com Flyway próprio; ligado por `plataforma.central.habilitado` | `br.com.plataforma:plataforma-comum-central` |
| `plataforma-comum/plataforma-comum-teste/` | Apoio aos testes (escopo `test`): `PostgresDeTeste` (Postgres descartável na imagem do parent) e `RegrasDeArquitetura` (regras ArchUnit comuns) | `br.com.plataforma:plataforma-comum-teste` |
| `pom.xml` (raiz) | Só agrega os módulos; todos saem com a mesma versão | não é publicado |

O módulo seguinte (`central`) entra em outro pull request.

Pacote `br.com.plataforma.comum.seguranca`: `HmacAssinatura` (um lado assina, o outro confere) e `Totp` (RFC 6238). Pacote `br.com.plataforma.comum.seguranca.login`: `LimiteLogin` (limite de tentativas por IP e por conta, antes do BCrypt), `ContadorJanelas` (a interface do contador), `ContadorEmMemoria` e `LimiteLoginException` (`RuntimeException` com os segundos de espera e o código `LOGIN_LIMITADO`). Cada sistema entrega o contador, o `Clock` e o sal pelo construtor e mapeia a exceção para HTTP 429.

### Módulo web (1.1.0)

Pacote `br.com.plataforma.comum.web`. Basta ter a dependência: a autoconfiguração registra o `RequestIdFilter` (X-Request-Id, MDC `requestId`), o `LimiteCorpoFilter` (1 MiB por padrão; multipart é conferido primeiro e segue só `spring.servlet.multipart`, mesmo com `Content-Length`; o limite vale para `getInputStream()` e `getReader()`; estouro lido antes do MVC, como no filtro da integração, vira 413 do próprio filtro e, dentro do MVC, 413 no handler, nunca 500) e o `GlobalExceptionHandler`, todos cedendo a um bean do sistema com o mesmo nome/tipo. Propriedades `plataforma.web.*`: `limite-corpo-ativo` (true), `limite-corpo-bytes` (1048576), `prefixo-codigo-proprio` (`br.com.`, usado no log do 500).

- Todo erro sai como `ApiError` (`timestamp, status, error, message, codigo, path, requestId, fieldErrors`), inclusive 404/405/415 do MVC (código `NAO_ENCONTRADO` no 404), 409 `CONFLITO_EDICAO` (lock otimista), 413 `CORPO_EXCEDIDO` e 429 do limite de login. Exceção de negócio: estenda `ApiException` ou use `BadRequestException` (`DADOS_INVALIDOS`), `ConflictException`, `ForbiddenException`, `UnauthorizedException`, `ResourceNotFoundException`, `TooManyRequestsException` (os cinco últimos sem código padrão).
- O 500 devolve mensagem genérica com o requestId e vai para o log **sem dados** (classes da cadeia de causas e até 5 pontos do código do sistema; nunca mensagem nem pilha completa, por causa da LGPD).
- Para saber dos erros (ex.: relatório de erros do Servirea), declare um bean `OuvinteDeErros`.
- Fica de fora (é do domínio de cada sistema): `Formatos` (CPF, CEP...), exceções com regra própria (ex.: `ValidacaoException` 422 do consultoria-app) e o `Retry-After`, que os controllers de login e MFA põem.

### Módulo monitoramento (1.2.0)

Pacote `br.com.plataforma.comum.monitoramento`. A autoconfiguração publica o `MetricasController` (`GET /monitoramento/metrics`, `@PreAuthorize("hasRole('MONITORAMENTO')")`, `Cache-Control: no-store`). O sistema faz duas coisas: (1) na cadeia de segurança, `addFilterBefore(new MonitoramentoFilter(token), JwtAuthenticationFilter.class)` com `monitoramento.token` (env `MONITORAMENTO_TOKEN`, 32 a 128 caracteres `[A-Za-z0-9_-]`; sem token a coleta fica fechada com 401) e `@EnableMethodSecurity`; (2) se tiver métricas próprias, um bean `MetricasDeDominio` que escreve em `SaidaPrometheus` (só agregados; se lançar exceção o grupo é omitido). Métricas comuns: `ecossistema_http_servidor_duracao_seconds`, `ecossistema_http_cliente_duracao_seconds` (por método e classe de status), JVM, processo e Hikari. Fica nos sistemas: o bloco de domínio (Central: instâncias por nível; Servirea: fila de envios), o log de requisição lenta e o `logback-spring.xml` do Servirea.

### Módulo teste (1.3.0)

Pacote `br.com.plataforma.comum.teste`, sempre com `<scope>test</scope>`. `PostgresDeTeste.iniciar(banco, usuario, senha)` sobe um Postgres descartável (tipo `org.testcontainers.postgresql.PostgreSQLContainer`, o do Testcontainers 2; o antigo `containers.PostgreSQLContainer` está deprecado) com a imagem da propriedade `plataforma.postgres.imagem` do parent (padrão `postgres:18-alpine` quando o teste roda fora do Maven); guarde o container num campo `static` da classe base dos testes de integração e chame `PostgresDeTeste.registrar(registry, container)` num `@DynamicPropertySource`. `RegrasDeArquitetura` traz as regras do `ArquiteturaTest` que valem para todos: `CONTROLLER_SO_FALA_COM_SERVICE`, `CONTROLLER_NAO_ABRE_TRANSACAO` (Spring e Jakarta), `NADA_DEPENDE_DE_CONTROLLER`, `JACKSON_TRES`, `SEM_INJECAO_POR_CAMPO`, `SEM_JAVA_UTIL_LOGGING`, `SEM_SAIDA_PADRAO` e `sqlNativoSoEm(lista)` (pega o JDBC do Spring em qualquer forma: `JdbcTemplate`/`JdbcOperations`, `NamedParameterJdbc*`, `JdbcClient`, `SimpleJdbcInsert`/`Call`; o JDBC cru com `Connection`/`Statement`; qualquer `createNative...`, `@Query(nativeQuery = true)` e `@NativeQuery`) com `exigirQueAsExcecoesExistem(...)` para a lista de exceções. A lista é pelo **nome completo** da classe (classe interna com `$`). Controller é `@RestController` ou `@Controller`; repositório é nome em `Repository` ou `Repositorio`, ou subtipo do `Repository` do Spring Data. Cada sistema chama `regra.check(codigo)` e mantém no seu teste o que é só dele (a Central não é multi-tenant, por exemplo) e a sua lista de SQL nativo. As regras citam as classes do Spring por nome, então o módulo não força dependência no sistema.

### Módulo auth (1.4.0; e-mail e redefinição de senha na 1.9.0)

Pacote `br.com.plataforma.comum.auth`; só liga com `plataforma.auth.habilitado=true`. O sistema entrega duas coisas: um bean `UsuariosDaAutenticacao` (`buscarPorLogin` e `versaoDeCredenciais(sujeito)`, vazio quando o usuário não existe ou está inativo) e um `PasswordEncoder`. Papéis, permissões, tenant e o contexto de segurança continuam no sistema, montados a partir do `JwtService.Token` que o módulo devolve.

- **`Autenticador`**: `entrar` (limite de tentativas, senha comparada mesmo sem usuário, mensagem única, MFA), `renovar`, `sair`, `encerrarSessoes`, `novaSessao` e `autenticar`/`autenticarSuporte` (assinatura, propósito, validade **e** `cv` igual à versão atual do usuário; a validação sem essa comparação não é pública). O controller só traduz para HTTP (cookie, `Retry-After` do `LimiteLoginException`, `MfaException`).
- **`JwtService`**: HMAC, `sub`, `purpose`, `cv`, `iss` e `exp` obrigatórios na validação, 15 minutos (configurável de 30 s a 1 h). `plataforma.auth.jwt.emissor` (um por aplicativo) e `plataforma.auth.login.sal` são obrigatórios com o módulo ligado, sem valor padrão (o sal não deriva mais do segredo do JWT: trocar o segredo zeraria os contadores). Cada validação diz qual propósito aceita: `access` ou `suporte` (sessão de suporte: operador e motivo no token, prazo limitado por `jwt.suporte-ttl-max`, auditoria é do sistema).
- **`RefreshTokens`**: opaco, só o SHA-256 no banco, rotação a cada uso; reuso de token revogado revoga todas as sessões do sujeito **e a revogação é confirmada antes do 401** (lock consultivo por sujeito numa transação própria, `REQUIRES_NEW`: vale mesmo quando o sistema chama a renovação dentro do seu `@Transactional`). Cada token guarda a versão das credenciais do login, e a rotação o recusa quando ela mudou (login que correu junto com a troca de senha ou a ativação do MFA). O contador do limite de login também grava em transação própria: o 401 de senha errada desfaz a transação do sistema, não a tentativa contada. Preferível chamar `entrar`/`renovar` **fora** de transação: dentro funciona, mas cada chamada segura uma segunda conexão do pool enquanto a de fora espera. Troca de senha/MFA: `encerrarSessoes` apaga as sessões (apagar, não revogar, para não contar como reuso).
- **`CookieDeRefresh`** e **`PoliticaCsrf`**: nome, caminho, domínio, `Secure` e `SameSite` por aplicativo; `SameSite=None` sem `Secure` impede a subida; CSRF opcionalmente só quando o cookie do refresh vem na requisição. Na cadeia de segurança use as três peças: `csrfTokenRepository(politica.repositorio())`, `csrfTokenRequestHandler(politica.tratador())` (o `spa()` do Spring Security: aceita o valor cru do cookie no cabeçalho; sem ele toda escrita do front vira 403) e `requireCsrfProtectionMatcher(politica.exigido())`.
- **`Mfa`**: TOTP com segredo cifrado (AES-GCM, chaves em `plataforma.auth.mfa.chaves`, contexto por aplicativo), códigos de recuperação com hash, cada código usado uma vez (atômico). A senha atual e a auditoria ficam com o sistema, que chama `preparar/ativar/desativar` depois de conferir a senha.
- **Banco**: schema `plataforma` com histórico próprio (`plataforma.historico_migracao`), scripts em `classpath:plataforma/db/auth`, rodados na subida **sem criar bean `Flyway`** (o do Spring Boot só liga se não houver nenhum; o do sistema segue intacto, o que um teste prova). O usuário do banco precisa poder criar o schema; use `plataforma.auth.migracao.url/user/password` se o usuário de execução não puder.
- **Papéis do banco**: com migrador e app separados (`MIGRATION_DB_*`), configure `plataforma.auth.migracao.url/user/password` (o migrador cria o schema) e `plataforma.auth.migracao.papel-app` (o papel da API recebe uso do schema e SELECT/INSERT/UPDATE/DELETE, nunca o histórico do Flyway; reaplicado a cada subida). Sem separação, nada a configurar.
- **Claims do sistema**: `emitirAcesso(sujeito, versao, extras)` aceita claims próprios (tenant, papéis), recusando os nomes do módulo (`sub`, `purpose`, `cv`, `exp`, `iat`...); eles voltam em `Token.extras()`. O propósito de sessão de suporte se chama `suporte` (no Servirea era `suporte_app`).
- **Propósitos do aplicativo (1.7.0)**: `plataforma.auth.jwt.propositos.<nome>=<validade>` (30 s a 1 h; minúsculas e `_`; `access` e `suporte` são reservados) declara tokens curtos do fluxo de login, como o `tenant_selection` do Servirea (a escolha da paróquia depois da senha). `JwtService.emitir(proposito, sujeito, versao, extras)` emite e `Autenticador.autenticarComo(token, proposito)` valida, conferindo também o `cv` (trocar a senha invalida o passo). Um token deste tipo nunca vale como acesso ou suporte.
- **Login em dois passos (1.7.0)**: `Autenticador.verificarCredenciais(login, senha, mfa, ip)` faz limite, senha e MFA e devolve a `Identidade` (`sujeito` e `versao`, sem o hash da senha) **sem abrir sessão** (`entrar` é ele mais `novaSessao`); `novaSessao(sujeito, versao, ip, extras)` abre a sessão com claims do sistema. `renovar(refresh, ip, extrasDoSujeito)` roda a função do sistema **dentro da transação da rotação**, depois de token, usuário e versão conferidos e antes de gravar o refresh novo: o que ela devolver vai para o access novo, e uma exceção dela (um 403 por falta de vínculo) desfaz a rotação, com o refresh antigo ainda válido e sem contar como reuso. A função não deve demorar nem chamar o `Autenticador` (a trava do sujeito está presa).
- **Suporte (1.7.0)**: `emitirSuporte(..., extras)` leva claims do sistema; `UsuariosDaAutenticacao.versaoDeSuporte(sujeito)` (por padrão igual a `versaoDeCredenciais`) permite que o sujeito do token de suporte não seja um usuário. O sistema que usa um código de uso único como sujeito responde com o que ainda vale na janela da sessão (código já trocado e dentro do prazo), não com "código não usado".
- **Bloqueio do login (1.7.0)**: `LimiteLoginException.primeiroBloqueio()` é verdadeiro só na tentativa de número limite+1 (no IP ou na conta) de cada janela; as seguintes apenas recebem o 429. Serve para auditar o bloqueio sem uma linha por tentativa.
- **Renovar os códigos de recuperação (1.8.0)**: `Mfa.renovarRecuperacao(sujeito, codigo)` troca os 10 códigos por novos (os antigos, usados ou não, deixam de valer), exige um código válido (do aplicativo ou de recuperação, que é consumido), responde `MFA_INATIVO` se o MFA não está ativo e encerra as sessões, como `ativar`. O limite de tentativas é da rota do sistema, como em `desativar`.
- **Limite nas rotas de MFA**: `Mfa.ativar`/`desativar` não limitam tentativas; o controller do sistema deve chamar o `LimiteLogin` antes, como a Central faz hoje.
- **E-mail e redefinição de senha (1.9.0)**: tudo desligado por padrão, em `plataforma.auth.email.*` e `plataforma.auth.redefinicao.*`. Nada mudou em `AuthProperties` nem em `UsuariosDaAutenticacao`: quem não liga não percebe a versão. Ligar a redefinição sem o e-mail não sobe.
  - **Envio** (`plataforma.auth.email.habilitado=true`): `EnviadorDeEmail` com o provedor `resend` (HTTP, `Authorization: Bearer`, prazos de conexão e resposta, nenhum redirecionamento seguido, chave `plataforma.auth.email.resend.api-key` só do ambiente e sem valor padrão) ou `log` (padrão: não envia e registra só que houve envio, nunca destinatário, assunto, link nem token; avisa na subida). `remetente` (`Nome <endereco@dominio>`, de domínio verificado no provedor) e `nome-app` são obrigatórios e vêm da configuração de cada app. Um bean `EnviadorDeEmail` do sistema toma o lugar (serve para o teste do app capturar o link). Falha do provedor vira `EnvioDeEmailException` sem endereço, chave nem corpo da resposta.
  - **Conteúdo** (`EmailsDeAcesso.enviarRedefinicao/enviarConvite`): só o nome do app, uma frase fixa e o link, em texto e em HTML (com o escape devido); nunca nome nem dado de aluno, paroquiano ou qualquer pessoa. O link precisa ser `https` (`http` só para localhost) e o endereço vem do cadastro do sistema, nunca do que foi digitado.
  - **Pedido** (`RedefinicaoDeSenha.solicitar(email, ip, buscarPorEmail)`): conta o pedido por IP e por e-mail **antes** de procurar a conta (limite próprio, sal derivado, que não se mistura com o do login; `LimiteLoginException` com o `Retry-After`) e volta sem dizer se a conta existe. A busca, a gravação do link e o envio rodam depois, num `DespachoDeEmail` (thread virtual; um bean do sistema toma o lugar), então o tempo da resposta é o mesmo exista ou não a conta; falha de envio só vai para o log como nome da classe. A rota do app responde 202 sempre.
  - **Link**: token opaco de 256 bits, **só o SHA-256 no banco** (`plataforma.redefinicao_token`, migration `V2`), uso único, 30 minutos (`prazo`, de 5 min a 24 h); pedir um novo invalida o anterior da mesma finalidade. O link é `url-base#token=...`: o token no fragmento não vai para log de proxy nem para o `Referer`; o front lê `location.hash`, manda o token no corpo do POST e limpa o fragmento.
  - **Confirmação** (`redefinir(token, novaSenha, codigoMfa, ip, troca)`): limite por IP e por link (trava a adivinhação do código do MFA); numa transação só, confere o link (desconhecido, vencido, usado ou de conta inativa dão o mesmo `LINK_INVALIDO`, 400), o **MFA quando ativo** (`MFA_NECESSARIO`/`MFA_CODIGO_INVALIDO`; com erro nada muda e o link segue valendo, dentro do limite), chama a `TrocaDeSenha` do sistema (grava o hash **e sobe a versão das credenciais**, na transação do módulo) e apaga os links do sujeito. Depois do commit, `encerrarSessoes`; os access tokens antigos já caíam pelo `cv`. A regra de força da senha é do app (o módulo só exige que exista).
  - **Convite**: `RedefinicaoDeSenha.emitirConvite(sujeito, prazo)` devolve um token (prazo do app, de 1 minuto a 30 dias) que se usa no mesmo `redefinir`; o app monta o link, grava o que quiser dele e envia com `EmailsDeAcesso.enviarConvite(para, link)` **depois do commit**. Convite novo invalida o anterior; pedir "esqueci a senha" não derruba o convite, mas usar um dos dois apaga os outros do sujeito. Um app que já gera o próprio link de convite (consultoria-app) só chama `enviarConvite`: o módulo não guarda o link.
  - **Fica no app**: as rotas (`Retry-After` no 429, 202 no pedido), a tela, o cadastro de usuário e a força da senha, a função de busca por e-mail e a `TrocaDeSenha`.
- **Nomes de bean** com prefixo `plataforma` (não colidem com um `JwtService` ou `CookieDeRefresh` que o sistema ainda tenha durante a adoção). Testado em Postgres 17 (produção) e 18.
- Fica nos sistemas: o filtro do Bearer e a montagem do `Authentication`, os controllers, o cadastro de usuário e a senha, as rotas e telas do "esqueci a senha" (a lógica é do módulo desde a 1.9.0), o tenant do Servirea, os limites extras do consultoria-app (cadastro, convite, refresh) e a auditoria. Na adoção: acrescentar `plataforma.*` na limpeza de tabelas dos testes de integração; migrar `operador.mfa_*`, `refresh_token` e `login_tentativa` existentes (ou recomeçar, antes do primeiro cliente).

### Módulo central (1.5.0)

Pacote `br.com.plataforma.comum.central`; só liga com `plataforma.central.habilitado=true`. É o lado do app do contrato `docs/contrato-integracao-v1.md` da Central, comparado entre Servirea e consultoria-app (divergências no relatório da Fase 4). O contrato manda; onde os dois apps divergem, o módulo segue o contrato.

- **`IntegracaoFiltro`** (entrada): chave conhecida → janela de 300 s → assinatura em tempo constante → nonce novo (gravado em transação própria só depois da assinatura válida), com os códigos 401 `CHAVE_DESCONHECIDA`, `TIMESTAMP_FORA_DA_JANELA`, `ASSINATURA_INVALIDA` (inclusive cabeçalho fora de `v1=` + 64 hex minúsculos, conferido antes de ler o corpo) e `NONCE_REPETIDO`, 413 `CORPO_EXCEDIDO` (1 MiB, também sem `Content-Length`). Cabeçalho ausente ou mal formado cai no código do passo correspondente (sem chave: `CHAVE_DESCONHECIDA`; sem timestamp: `TIMESTAMP_FORA_DA_JANELA`; sem nonce ou assinatura: `ASSINATURA_INVALIDA`). A assinatura cobre o `getRequestURI()` bruto mais a query string, como enviados. **Não se registra sozinho no contêiner**: o sistema o põe numa cadeia própria de segurança (`/integracao/**`, sem JWT, CSRF nem sessão) com `addFilterBefore(filtro, AuthorizationFilter.class)` e exige a autoridade `PERM_INTEGRACAO`; o id da chave fica no atributo `IntegracaoFiltro.ATRIBUTO_CHAVE`. O módulo publica o registro dele no contêiner como **desabilitado** (`plataformaIntegracaoFiltroRegistro`), para o Spring Boot não o registrar também em `/*` (validaria duas vezes, com possíveis chaves diferentes, na adoção gradual).
- **Chaves** (`plataforma.central.chaves-entrada`): `id:base64[,id:base64]`, no máximo duas (troca sem parada), segredo de pelo menos 32 bytes, ids únicos; configuração inválida derruba a subida (nada de chave ignorada em silêncio). O segredo nunca vai para log nem mensagem de erro.
- **`CentralClient`** (saída, só com `plataforma.central.central-url`): cinco cabeçalhos do contrato, nonce novo a cada envio, exige `https` (`http` só para localhost: as respostas da Central não são assinadas; com `plataforma.central.rede-interna=true` também `http` para um nome de serviço da rede interna, um só rótulo sem ponto e sem número IP, como `central-api` no compose, que não resolve fora dela), sem seguir redirecionamento, prazos de conexão e resposta (o da resposta vale também para a leitura do corpo: uma Central lenta não prende a thread), limite de tamanho da resposta; falha de rede vira `CentralIndisponivelException` (o chamador repete com espera, conforme a tabela de erros do contrato).
- **`Idempotencia`**: `provisionar(chave, contratacaoId, ...)` recusa (400) chave diferente do id da contratação; mesma `Idempotency-Key` e mesmo corpo repete a resposta gravada sem repetir o efeito, com **200** e `Idempotency-Replayed: true` (`Resultado.comoResposta()` monta a resposta HTTP); outro corpo ou tipo é 409 `IDEMPOTENCY_KEY_CONFLITO`. Requisições simultâneas com a mesma chave se serializam por lock consultivo, e a operação roda na mesma transação do registro (falhou, nada fica gravado). Efeitos externos (e-mail do convite) só depois do commit e só quando `Resultado.repetido()` é falso.
- **`DireitosLocais`**: versão maior é aplicada; versão **igual** só renova `confirmadoEm` (a regra do contrato; o Servirea hoje aplica também em versão igual, e o módulo não); versão **menor** não muda nada (um webhook atrasado não estende a janela de acesso). `acessoEfetivo = acessoLiberado E (agora − confirmadoEm) ≤ tolerância` (padrão 72 h, `plataforma.central.tolerancia-horas`); sem registro, o acesso é negado. `sincronizar` aplica as maiores e confirma **todas** as presentes (inclusive de versão igual ou menor) e devolve `Sincronizacao(aplicadas, desconhecidas, falhas)`: um item com conflito ou dado inválido não interrompe os seguintes (senão a repetição de 30 min cairia sempre nele e, às 72 h, os que vêm depois perderiam o acesso); o chamador alerta com as listas. Cada item roda numa transação própria, então chamar de um job `@Transactional` é seguro.
- **Banco**: schema `plataforma_integracao` (separado do `plataforma` do auth: o Flyway recusa schema não vazio sem o seu histórico) com `historico_migracao` próprio, scripts em `classpath:plataforma/db/central`, **sem bean `Flyway`**. Chave da instância é um texto (`instancia_id`: tenant no Servirea, consultoria no consultoria-app). `plataforma.central.migracao.*` e `papel-app` funcionam como no auth.
- **Nomes de bean** com prefixo `plataforma`; todos cedem a um bean do sistema do mesmo tipo.
- Fica nos sistemas: os controllers das rotas `/integracao/v1/**` (provisionar, consultar, webhook, código de suporte, catálogo), o que provisionar significa em cada produto (criar tenant, consultoria), o agendador da sincronização (8 h, retry de 30 min, alerta às 24 h, bloqueio às 72 h), o relato de erros de servidor à Central (6.2) e o consumo. Na adoção: trocar `direitos_locais`, `integracao_nonce` e `integracao_operacao` do sistema pelas do módulo (recomeçar, antes do primeiro cliente).

## Pacote web (TypeScript)

`web/` é o `@plataforma/web`: o que os fronts (Angular, Expo) precisam fazer **igual**, em TypeScript puro e sem dependência de runtime. Fica fora do reator Maven, com versão e tag próprias (`web-vX.Y.Z`), e é distribuído como `.tgz` numa Release do GitHub, sem token. Uso, entradas e publicação em [web/README.md](web/README.md).

## Como usar num sistema

1. No `pom.xml` do sistema:
   ```xml
   <parent>
     <groupId>br.com.plataforma</groupId><artifactId>plataforma-parent</artifactId><version>1.0.0</version>
   </parent>
   <repositories>
     <repository><id>github</id><url>https://maven.pkg.github.com/GustavoToebe/plataforma</url></repository>
   </repositories>
   <dependency>
     <groupId>br.com.plataforma</groupId><artifactId>plataforma-comum-seguranca</artifactId><version>1.0.0</version>
   </dependency>
   ```
   Copie também o `.mvn/jvm.config` da raiz deste repositório (aberturas do javac para o Error Prone).
2. O Maven precisa de um token com `read:packages` (servidor `github` no `settings.xml`). No GitHub Actions use `secrets.GITHUB_TOKEN` com `packages: read`; num build Docker ou local, um token pessoal passado como segredo de build, nunca gravado na imagem.
3. Fixe sempre a versão. Para atualizar, mude a versão no `pom.xml` do sistema e rode os testes dele.
4. Testes de integração com Postgres: leia a imagem da propriedade de sistema `plataforma.postgres.imagem` (o parent a repassa ao Surefire). Quem ainda não pode usar o 18 sobrescreve a propriedade no próprio `pom.xml`.

## Como publicar uma versão

1. Numa branch curta, mude a versão em todos os `pom.xml` (`mvn versions:set -DnewVersion=1.1.0`) e abra o pull request.
2. Com o CI do pull request verde, crie a tag `v1.1.0` na branch. O workflow testa e publica todos os módulos de uma vez (`deployAtEnd`).
3. Versões publicadas **não se alteram**: correção vira versão nova. O merge do pull request é do Gustavo, sem squash.

O pacote `web/` segue outro caminho: o workflow `web.yml` testa a pasta em todo pull request e, na tag `web-vX.Y.Z` (igual à versão do `web/package.json`), publica a Release com o `.tgz`. A tag `web-v*` não dispara o `java.yml`.

## Regras de mudança

- Mudou comportamento que os sistemas usam (ex.: formato da assinatura)? Suba versão **maior** e atualize os sistemas juntos.
- Mudança só interna ou correção compatível: versão de correção (1.0.0 para 1.0.1).
- Cada classe tem teste aqui. Os sistemas mantêm só os testes que dependem do seu domínio.

Maven Packages exige token pessoal classic com `read:packages` para leitura fora do Actions; fine-grained não é suportado. Ver a [documentação oficial](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages).
